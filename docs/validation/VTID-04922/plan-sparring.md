# Plan: Shared Live Room links show the room's own preview in WhatsApp (vitana-v1)

Change class: **standard** (a Supabase edge function changes; frontend share links change).
Owner report (2026-10-06, chat, with a WhatsApp screenshot from production): sharing a Live Room gives the generic "MAXINA - Longevity Community / Discover events and connect…" preview with the MAXINA logo, not that room's title and image.

<!-- plan:begin -->
## Context (verified by the planner)
- Live Room share links are built in two places as `${window.location.origin}/comm/live-rooms?live=<roomId>`: `EventLiveRoomCard` (`src/components/events/EventsLiveRooms.tsx`, its `SocialShareButton`) and 5 call sites in `src/pages/community/LiveRooms.tsx` (~L451, 484, 517, 554, 587, 620).
- That URL is a plain SPA route, so a crawler gets the static `index.html` with generic Open Graph tags — hence the generic preview.
- Rich previews exist for other content through the Cloudflare worker `vitanaland-og-proxy` (`vitana-platform/cloudflare/vitanaland-og-proxy/worker.js`), documented in `src/lib/shareUrl.ts` as bound to `vitanaland.com/(shorts|products|events|profiles)/*`. For crawlers it fetches the Supabase edge function `og-event?id=` (UUID) or `?slug=`; humans get a 302 to `https://vitanaland.com/?share=event&id=<id>` (`getRedirectUrl`, worker.js ~L485-501), which `src/pages/ShareEntry.tsx` turns into `/pub/events/<id>`.
- The worker also has a `rooms` type → `og-room`, but no `og-room` function exists in `supabase/functions` (only og-campaign, og-event, og-share, og-short) and the Cloudflare route binding for `/rooms/*` is configured in the Cloudflare dashboard, which this session cannot see or change. So `/rooms/...` is NOT a safe path to use.
- `og-event` (`supabase/functions/og-event/index.ts`) looks up `global_community_events` by slug or id, and serves the generic fallback HTML when nothing matches. Live rooms live in `community_live_streams` (SELECT policy: anyone may read status pending/live — migration 20251022080341), so `og-event` cannot find them today.
- Edge functions deploy to the live Supabase project only by manual `workflow_dispatch` of `supabase-functions-deploy.yml` (push deploys are frozen since the 2026-06-08 cutover; there is no staging functions environment). `og-event` is `verify_jwt = false` (config.toml L147).

## Change (nothing in vitana-platform or Cloudflare is touched)
1. **Share URL**: new helper `getLiveRoomShareUrl(roomId)` in `src/lib/shareUrl.ts` returning `https://vitanaland.com/events/<roomId>` — a path the worker already binds (documented list in shareUrl.ts: shorts|products|events|profiles), so crawlers reach `og-event`. ALL NINE call sites use it: `LiveRooms.tsx` ×6 (L451, 484, 517, 554, 587, 621), `EventsLiveRooms.tsx` (EventLiveRoomCard), `MobileLiveRoomCarousel.tsx:211`, and `LiveRoomDrawer.tsx:186` (`handleShare` copy-link). Old `/comm/live-rooms?live=` links already in the wild keep working as SPA routes (only without a rich preview).
2. **og-event**: only when there was NO slug match and NO `global_community_events` match, AND the `id` param is a valid UUID (never on slug-only lookups, so typo'd slugs cost no extra query), look the id up in `community_live_streams` mirroring the table's public read policy (status `pending` or `live`, or `ended` with `enable_replay = true`). Build the OG HTML from the room in a pure, testable function: title, description (the room's blurb, else the function's existing English default style "Join this live room on MAXINA"), image = `cover_image_url`, else the host's `profiles.avatar_url`, else the default image. Rooms' images use the Supabase render URL with `width=1200&height=630&resize=cover&quality=80&format=origin` (host avatars/covers can be multi-MB phone photos; WhatsApp drops images over ~600 KB and mishandles WebP — the worker's own documented constraint); events keep their current image handling (applying the same to events is a separate follow-up). `og:type` website. Canonical `https://vitanaland.com/events/<id>`; human destination `https://vitanaland.com/?share=room&id=<id>`.
3. **App entry, no new latency for events**: `ShareEntry.tsx` keeps its synchronous `share=event` branch exactly as is, and gains a synchronous `share=room&id=` branch (navigate to `/comm/live-rooms?live=<id>`, UTM kept; no fetch). The worker's human redirect for `/events/<uuid>` is `?share=event&id=<uuid>` → `/pub/events/<uuid>` (`PublicEventLanding`); there, ONLY when the event is not found, one read-only GET of `community_live_streams` for that id decides: found → `navigate('/comm/live-rooms?live=<id>', {replace:true})`; otherwise today's not-found screen. Events that exist see no extra query or flash.
4. **Tests**: Vitest for `getLiveRoomShareUrl`; Vitest for the pure og room-HTML builder (escaping, image order, canonical/destination, UUID guard); Vitest for the ShareEntry `share=room` branch and the PublicEventLanding not-found → live-room redirect; a source-level Vitest asserting no `/comm/live-rooms?live=` share-link construction remains in the nine call sites. Read-only staging spec: a GET of the og-event function with a WhatsApp user-agent for a real scheduled room's id asserts `og:title` = the room title and `og:image` is a Supabase image URL (no writes).
5. **Rollout**: merge → staging deploy + STAGING-VERIFY for the frontend; the og-event function is deployed to the live Supabase project by a manual `supabase-functions-deploy.yml` dispatch (`functions: og-event`) pinned to the verified commit, BEFORE the frontend publish (the function change is backward compatible — it only adds a fallback branch). The owner approves that function deploy in the ready message.
6. **Cache note**: WhatsApp caches a preview per URL for days. `https://vitanaland.com/events/<roomId>` has never been shared, so it is fetched fresh; the already-shared `/comm/live-rooms?live=…` message keeps its old preview.

## Decision record
`/rooms/<id>` + a new `og-room` function (the worker already routes `rooms` to it and redirects to `?share=room`) would be cleaner, but the Cloudflare route binding for `/rooms/*` cannot be seen or changed from here and shareUrl.ts documents the bound list as shorts|products|events|profiles. `/events/<id>` is the only verifiably bound path. If the owner later binds `vitanaland.com/rooms/*`, the `og-room` function can replace the og-event fallback; the new `share=room` ShareEntry branch is already forward-compatible with it.

## Out of scope
Cloudflare/worker changes, a dedicated `og-room` function, Telegram/other crawlers beyond what og-event already serves, previews for ended rooms, any DB migration.
